# WorldCast Live: the multiplayer web demo

A web page where several people play one recorded round start together. Each player's view is generated by their own
WorldCast client on their own GPU, from their keyboard and mouse; each client's state model supplies its player's
position, and the clients share only player state and scene state, as in the paper. No recorded positions steer the
world. The page has a lobby (create or join a room, pick a seat), the play view (the generated view, a minimap with
every player, input-to-photon latency and network quality) and a spectator view with every player's view at once.

Everything is in `demo/`; `tools/serve_demo.py` starts it. Without a GPU, workers run a mock engine that plays
pre-rendered frames and fakes the state model, so the whole system runs on a laptop.

## Try it on a laptop

```bash
pip install -r requirements/demo.txt          # aiohttp, numpy, pillow, pyyaml
python tools/serve_demo.py --role local --workers 2
```

Open <http://localhost:8100> in two browser windows, create a room, take a seat in each. The default library is a
synthetic grid arena that needs no files. For real WorldCast frames, build a library from rendered clips
([Library](#library)) and pass it: `--set library=runs/demo-library/library.json`.

Controls: click the view to capture the mouse. `W A S D` move, mouse looks, left / right button fire / alt-fire,
`Space` jump, `C` or `Ctrl` crouch, `Shift` walk, `1`-`4` weapons, `Q` last weapon, `R` reload, `F` inspect, `Esc`
pauses. Click the HUD's latency number for the breakdown. Phones can hold a seat and watch it live (playing needs a
keyboard and a mouse).

## Architecture

```
 browsers                         coordinator (1, CPU)                       GPU workers (1 per GPU, 1 player each)
 ────────                         ────────────────────                       ──────────────────────────────────────
 lobby page ── HTTP /api ───────▶ rooms, seats, library        ◀── WS ───── worker A: engine (models loaded once)
            ◀─ WS /ws/lobby ────  room clock, worker registry  ─── assign ─▶   input buffer ─▶ step ─▶ JPEG
                                  relay of the shared world:   ◀── state ──    own state per block
 play view ═ WS /ws/play ══════════════════════════════════════════════════▶ worker A  (inputs in, frames out)
 spectator ═ WS /ws/watch ═════════════════════════════════════════════════▶ every worker of the room
                                  · player state (each block)  ─── relay ──▶ worker B, C ...
                                  · peer messages (scene-state blocks, step records), kept for late joiners
```

**Coordinator** (`demo/coordinator.py`, one process, no GPU). Serves the page and the lobby API, keeps the rooms (a
round start from the library, a sync mode, the seats) and the registry of workers. A join takes a free worker and
assigns it the seat; the browser then talks to that worker directly. Per room it relays what the paper's clients
exchange and nothing else: every player's own state once per block (from its state model), and the engines' peer
messages (scene-state blocks, step records). It keeps the last `coordinator.scene_blocks_per_player` scene-state
blocks of each player (the memory bound B) and sends them to a player who joins late. It also owns the room clock:
workers synchronise to it (NTP-style pings), so the states they publish carry comparable room times.

**Worker** (`demo/worker.py`, one per GPU). Loads its engine once and serves one player at a time. Per block it cuts
the player's inputs into the block's controls, steps the engine, and streams each frame to the player (and to
spectators) the moment it is decoded. After the block it publishes the player's states and the engine's peer
messages to the coordinator, and it hands the peers' states and messages it receives to its engine.

- *Pacing.* A block starts just in time: its first frame should reach the browser when the previous block's frames
  run out. So inputs are taken as late as possible, and a fast engine does not run ahead of the display. The start
  time is the slowest critical delay of the last 16 blocks plus 40 ms of margin.
- *Sync.* `async` (default): a client steps on its peers' latest states, extrapolated over a block, so one slow
  player does not stall the others. `lockstep`: before block `b` a worker waits (up to `worker.lockstep_timeout_s`)
  for every peer's block `b - 1`, as in the paper's evaluation. Blocks are numbered on the room clock, so a late
  joiner's block `b` is everyone's block `b`.

**Engine** (`demo/engine.py`, `EngineProtocol`). The seam between a worker and the model:

| call | meaning |
|---|---|
| `start(round_start, seat, peers)` | open a session at the round start (models stay loaded) |
| `step(controls)` | generate the next block: call `controls()` once, right before the denoising ladder, and yield the block's `Frame`s as they are decoded (RGB, or JPEG if the engine encodes) with the player's own state and the peers where this client placed them |
| `receive_state(state)` | a peer's newest player state |
| `take_messages()` / `receive_message(msg)` | opaque peer messages; kind `scene` is kept for late joiners |
| `remove_peer(seat)`, `stats()` | a peer left; numbers for the HUD |

`demo/mock_engine.py` implements it without a GPU: it sleeps `step_ms` (the ladder) and `decode_ms` per frame, plays
a seat's pre-rendered clip (or draws the grid arena with the other players in it), integrates the controls into a
position (run / walk / crouch speeds, jump and gravity, kept inside the walkable area of the map's radar image),
extrapolates the peers' states over at most one block, and publishes scene-state blocks of the real size (774 kB)
so the relay carries the real traffic. `demo/worldcast_engine.py` adapts `worldcast.engine.realtime.Engine` (see
[GPU integration](#gpu-integration)).

**Browser** (`demo/static/`, plain ES modules, no build step). `app.js` (router, lobby, seat picker), `play.js` (input,
HUD, latency), `stream.js` (frame stream: WebSocket, JPEG decode with `createImageBitmap`, a jitter buffer that shows
frames at an even 16 fps), `minimap.js`, `watch.js` (spectators). Fonts and tokens follow the project page.

## Protocol

HTTP (coordinator): `GET /api/lobby` (round starts, rooms, workers, play settings), `POST /api/rooms`
`{round, sync}`, `GET /api/rooms/<id>`, `POST /api/rooms/<id>/join` `{seat, name}` (returns the player's
`play_url` and a token), `GET /library/<file>` (previews and radar images). WebSockets: `/ws/lobby` (live rooms),
`/ws/worker` (workers), `/ws/proxy/<worker>/<play|watch>` (see `media_route`). Workers: `/ws/play?token=`,
`/ws/watch?room=`, `/health`.

Text messages are JSON `{"t": type, ...}`. Binary messages are `u32 header length | JSON header | payload`.

| direction | message |
|---|---|
| browser → worker | `in` {`q` sequence, `b` held buttons, `dp` `dy` degrees turned since the last tick, `w` weapon id}, sent once per display frame and at once on every key or button change; `ping`; `bye` |
| worker → browser | `welcome`, `status`, `roster`, `pong`; binary frames: header {`k` frame, `b` block, `q` newest input tick in the frame, `rt` room time, `tm` [input tick → controls taken, controls taken → frame ready, encode] ms, `s` own state, `p` peers' states}, payload JPEG |
| worker → coordinator | `hello`, `assigned`, `status`, `state` {`block`, `frames`: the block's states}, `left`, `clock`; binary `msg` {`kind`, `block`, `meta`} + payload |
| coordinator → worker | `welcome`, `assign` {room, round, seat, token, sync, room clock origin}, `roster`, relayed `state` and `msg`, `clock` |

A player state on the wire: `[seat, room time, x, y, z, yaw, pitch, alive, weapon, buttons, vx, vy]` (engine units
and degrees; yaw counter-clockwise from +x, pitch > 0 looks down).

Actions follow `worldcast/data/actions.py`: bit `i` of `b` is `PAPER_ACTION_BUTTONS[i]` (forward, back, move_left,
move_right, jump, duck, speed, attack, attack2, reload, look_at_weapon); a mouse move turns
`play.mouse_degrees_per_pixel` degrees per pixel (adjustable on the pause screen); `w` is a 52-way fine weapon id of
the seat's loadout. The worker folds a block's ticks into the model's per-frame controls (`demo/actions.py`): 11
buttons, the turn mu-law encoded (`noclip`, as the paper's weights were deployed), the weapon id, and the 1/64 s
substeps of the peer material. `play.action_mapping` chooses how: `latest` (default) holds the buttons held at the cut
for every frame, adds the buttons tapped since the previous block to its first frame and spreads the turn over the
block, so an input shows from the block's first frame on; `realtime` puts each tick on the frame of its own 1/16 s,
as in the recorded data, at the price of about one more block of latency.

## Latency

The HUD's number is input to photon: from each key press, click or mouse-move onset (its browser event time) to the
moment the first frame that folds in that input is drawn, the median over the last 24 inputs. The breakdown panel
splits it, per input, into sampling (event to tick sent), network, waiting for the next block to start, generating
(controls taken to frame ready), encoding and the jitter buffer; the worker reports its parts per frame, so no clock
synchronisation between browser and worker is needed. The network bars combine the round trip (pings every second)
and the stalls of the last 10 s.

With blocks of `F` frames at 16 fps and a ladder of `L` ms, an input waits on average half a block for the next block
to start, then the ladder: input to photon ≈ `F × 62.5 / 2 + L + buffer + network`.

Measured on a MacBook (Apple silicon) with the mock engine, three workers, three headless Chrome players and one
spectator, all local, while the machine was heavily loaded by other jobs (load average 15-50); 24 inputs per player
and run, ranges over three runs (one run for the 16-frame row):

| mock timing | input → photon, median (p10-p90) | waiting for block | generating | jitter buffer | network + encode + sampling | stalls / 10 s |
|---|---|---|---|---|---|---|
| 4 frames per step, 180 ms ladder (`demo.yaml`) | 385-449 ms (p10 305-345, p90 478-537) | 114-135 ms | 184-193 ms | 69-110 ms | 11-15 ms | 0 |
| 16 frames per step (the paper's block), 550 ms ladder (`mock_block16.yaml`) | 1213 ms (672-1641) | 495 ms | 563 ms | 114 ms | 16 ms | 0-1 |

Everything the demo adds on top of the engine (sampling, network on a LAN, encoding, buffer) is about 100 ms; the
rest is the block structure and the ladder. What lowers it on a GPU: early prefill (only the ladder waits for the
controls), CUDA graphs, decoding while the next block generates (all options of `worldcast.engine.realtime`), and a
smaller `PACING_MARGIN_S` (`demo/worker.py`) on a quiet machine.

Bandwidth per player: about 43 kB per JPEG frame at quality 85 (672 x 384), so 5.5 Mbit/s down; inputs are about
60 ticks/s of under 100 bytes. Between workers, each scene-state block is 774 kB, pushed to every other worker of the
room: with 10 players at one block per second, each worker receives about 56 Mbit/s and the coordinator sends about
0.6 Gbit/s, which a datacenter network carries; across the internet, lower `scene_blocks_per_player` is not enough
and peers should fetch blocks on demand instead (a change in the coordinator only).

## Run on GPUs, across machines

One coordinator anywhere reachable by browsers and workers; one worker per GPU. Every host reads the same library
file (a shared file system or a copy); GPU workers also need the inference configs and data of the README.

```bash
# the coordinator (CPU host "lobby"), port 8100
python tools/serve_demo.py --role coordinator --set library=/data/demo-library/library.json

# one worker per GPU (GPU host "gpu-1"), ports 8101, 8102, ...
CUDA_VISIBLE_DEVICES=0 python tools/serve_demo.py --role worker \
    --set engine.kind=worldcast --set library=/data/demo-library/library.json \
    --set 'engine.worldcast.configs=[configs/infer/worldcast_4step.yaml, weights/paths.yaml, data/paths.yaml]' \
    --set worker.coordinator_url=ws://lobby:8100 --set worker.port=8101 \
    --set worker.advertise_url=ws://gpu-1:8101 --set worker.gpu_label="H20 #0"
CUDA_VISIBLE_DEVICES=1 python tools/serve_demo.py --role worker ... --set worker.port=8102 \
    --set worker.advertise_url=ws://gpu-1:8102
```

Browsers open `http://lobby:8100`. By default (`coordinator.media_route: direct`) they open each worker's WebSocket
directly, at `worker.advertise_url` (or the address the worker connected from). When browsers cannot reach the GPU
hosts (a private cluster network), set `--set coordinator.media_route=proxy` on the coordinator: frames and inputs
then pass through it, at one extra hop of latency. Behind HTTPS, put the coordinator behind a TLS proxy and use
`proxy` (the page then opens `wss://` on its own host). Ports: the coordinator's (8100) for browsers and workers;
each worker's for browsers (direct mode) or for the coordinator (proxy mode).

## Config

`configs/demo/demo.yaml` holds every setting with its default; `--config` merges further files in order and `--set
key=value` overrides one dotted key (YAML-typed). A relative `library` path in a YAML file is relative to that file.

| section | keys |
|---|---|
| `library` | `library.json` of the round starts; `null` = the synthetic arena |
| `coordinator` | `host`, `port`, `media_route` (`direct` / `proxy`), `max_rooms`, `scene_blocks_per_player`, `empty_room_s` |
| `worker` | `host`, `port`, `coordinator_url`, `advertise_url`, `worker_id`, `gpu_label`, `jpeg_quality`, `reconnect_grace_s`, `lockstep_timeout_s` |
| `engine` | `kind` (`mock` / `worldcast`); `mock`: `frames_per_step`, `step_ms`, `decode_ms`, `jitter_ms`, `scene_block_frames`, `scene_block_bytes`; `worldcast`: `configs`, `overrides`, `realtime` (`RealtimeConfig` fields), `own_state` (`state_model` / `gt`) |
| `play` | `fps`, `jitter_buffer_frames`, `action_mapping` (`latest` / `realtime`), `mouse_degrees_per_pixel`, `default_sync` (`async` / `lockstep`) |

`configs/demo/mock_block16.yaml` switches the mock to the paper's 16-frame blocks.

## Library

A library is a `library.json` next to its images: round starts, each with a map, a start frame (source frame, 32 fps),
an optional radar image with its transform, a cover seat, and seats (`seat`, `media_id`, `team`, `spawn` [x, y, z, yaw,
pitch], `loadout`, `preview`, and for the mock engine `clip`, a directory of JPEG frames). The GPU engine needs round
starts whose start frame has a cached first latent (`docs/data.md`), usually 0.

`tools/build_demo_library.py --manifest library.yaml --out runs/demo-library` builds one from a short manifest (format
in the script's docstring): per round, the rendered video of every seat (the mock's clips and the seat previews), the
round's OpenCS2 tick tables (each seat's spawn pose, team and weapons at the start) and the map's nav mesh (the radar
image: walkable floor shaded by height; the mock engine also keeps players on it).

## Testing

`python -m pytest tests/demo -q`: a coordinator, three mock workers and three scripted players in one process, in
async and lock-step mode. It checks that every player gets 16 fps, that each player's frames carry the others'
state-model positions and see a moving player move, that a late joiner gets the earlier scene-state blocks, that a
taken seat is refused and that leaving frees the workers. The demo was also checked with headless Chrome over the
DevTools protocol (two players and a phone in one room, a spectator; key and mouse events; the numbers above).

## GPU integration

The GPU side is `worldcast.engine.realtime.Engine` (a separate change). `demo/worldcast_engine.py` maps it onto
`EngineProtocol`: it builds the `InferenceConfig` from `engine.worldcast.configs`, passes the block's controls as the
callable the engine calls right before its ladder, passes JPEG frames through, turns the engine's messages into peer
messages (`transport.encode` / `decode`) and reads positions for the HUD from the player-state messages. It was
written against the engine's first version and checked only against a stub of it. To finish:

1. Run it on a GPU against the merged `worldcast.engine.realtime`; adjust the adapter where the engine's API moved.
2. `own_state: state_model` needs the closed-loop state model (the state-model port) wired into the engine as its
   own-state source; until then `own_state: gt` runs the paper's recorded track.
3. Seats nobody plays: drop them from the player-state field (not alive) so no recorded position enters the world;
   the engine currently fills every seat of the round from the recording.
4. Room sync per room: the engine's `lockstep` is fixed when it is built; set it per session from the room's mode.
5. Round starts: the library's start frames must have cached first latents; late joiners need the engine to start
   from the room's current block (and, with scene state, to admit the earlier blocks it is sent).
6. Peer extrapolation: with `own_state: state_model`, peers are placed by `worldcast/player_state/extrapolate.py`; the mock's
   constant-velocity extrapolation is only for the HUD.
